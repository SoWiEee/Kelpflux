# 第一章 動機與問題

## 1.1 研究動機

近年來，人工智慧研究越來越依賴 GPU 進行訓練、推論與資料處理。然而在一般研究室的共享主機環境中，常常會遇到以下問題：

1. 一張 GPU 只給一個工作使用，實際利用率不高。
2. 多位使用者同時使用同一台機器時，容易互相干擾，缺乏公平的排隊與分配方式。
3. 長時間工作若中途被中斷，往往會造成時間浪費。
4. 沒有工作時，系統仍然維持大量資源待命，造成硬體閒置。

目前常見的系統大多只擅長其中一件事。例如，容器平台擅長自動啟動與回收資源，但對研究工作常見的 GPU 分配、批次排程與多使用者管理支援較弱；相對地，傳統高效能運算排程器雖然擅長管理工作佇列與硬體資源，但對彈性擴縮與雲端式管理不夠方便。

因此，本專題希望結合兩者優點，建立一套既能保有研究者熟悉的工作提交流程，又能做到動態分配 CPU、GPU 與儲存資源的系統。進一步地，我們也希望導入機器學習方法，讓系統可以根據目前佇列狀態與硬體使用情形，自動做出更合理的資源分配決策。

## 1.2 研究問題

本專題主要探討以下幾個問題：

1. 如何在容器化叢集上建立一套適合研究工作的排程平台。
2. 如何根據工作數量，自動增加或減少 CPU 與 GPU 計算節點。
3. 如何讓多個較小的 GPU 工作共享同一張顯示卡，以提升使用效率。
4. 如何利用深度強化學習模型，協助系統決定哪些工作應優先執行，以及應該使用哪些硬體資源。
5. 如何在模型判斷不可靠時，讓系統自動回到較穩定的基本排程方式。
6. 如何把整個系統的決策過程、資源變化與工作執行情況清楚地呈現出來。

# 第二章 方法與步驟

## 2.1 系統整體架構

本系統的核心概念，是把「批次工作排程」與「彈性資源管理」結合起來。使用者仍然以熟悉的方式提交工作，而系統在背後自動處理工作排序、節點啟動、GPU 分配與執行監控。

整體系統目前包含下列幾個部分：

1. **工作提交入口**：提供使用者提交與查詢工作的介面。
2. **中央排程控制**：負責接收工作、維護佇列、決定優先順序。
3. **CPU 與 GPU 計算節點**：實際執行工作的運算資源。
4. **彈性控制模組**：根據佇列長度與執行狀態，自動啟動或回收計算節點。
5. **智慧決策模組**：利用強化學習模型協助判斷工作排序與資源配置。
6. **監控與追蹤模組**：記錄系統狀態、工作過程與資源使用情況。

## 2.2 排程與資源分配流程

目前系統的決策流程可以分成三層。

### (1) 基本排程規則

當使用者提交工作後，系統會先補齊必要資訊，例如工作類型、所需記憶體與預設設定，再根據幾個簡單但穩定的規則來計算這個工作應有的優先程度。這些規則主要考慮：

1. 這個工作是否適合目前剩餘的 GPU 資源。
2. 是否會造成資源被切得太零碎。
3. 若能估計工作長度，較短的工作是否應該優先執行。

這一層相當於系統的保底機制，即使智慧模型失效，系統仍可正常運作。

### (2) 智慧決策模型

在基本規則之外，我們另外加入深度強化學習模型，讓系統可以根據「目前有哪些工作在等待」、「哪些節點正在執行工作」、「GPU 尚有多少可分配空間」等資訊，進一步判斷：

1. 哪一個工作應該優先處理。
2. 是否需要額外提高其優先順序。
3. 這個工作比較適合放到哪一個節點或哪一類 GPU 資源上。

如果模型發現目前資訊不足，或對自己的判斷沒有把握，系統就不採用模型決策，而是回到前述的基本排程規則。

### (3) 指定資源配置機制

除了影響工作的先後順序外，系統也能在特定情況下，先暫時保留工作，再根據模型決定它應該放到哪一台節點上，之後再正式釋放執行。這樣的做法可以讓模型的判斷不只停留在「哪個工作先跑」，而是更進一步參與「工作要放在哪裡跑」。

這部分目前已完成初步實作，並能在實際系統中進行驗證。

## 2.3 GPU 資源共享方法

在一般情況下，一張 GPU 往往一次只給一個工作使用，但很多研究工作其實無法完全吃滿整張卡。為了提升利用率，本系統採用 GPU 資源切分的方式，讓多個較小的工作共享同一張 GPU。

以目前的系統設定為例，一張 GPU 可以切成多個可分配單位。使用者可依工作需求申請較少或較多的份額，例如四分之一、二分之一，或整張卡。這樣的做法有兩個好處：

1. 小型工作不需要為了少量需求而獨占整張 GPU。
2. 系統可以更細緻地安排不同大小的工作，提高整體使用率。

## 2.4 模型訓練與評估方法

本專題希望採用的強化學習方法是 **Distributional Soft Actor-Critic for Risk-Sensitive Reinforcement Learning**。這裡的重點不是只讓模型預測「平均情況下哪個選擇最好」，而是讓模型學到「每個選擇可能造成的結果分布」。

以排程問題來說，同一個工作放到同一台節點上，不一定每次都有相同結果。可能受到下列因素影響：

1. 節點是否剛啟動，是否還在暖機。
2. GPU 是否被其他工作共享。
3. 工作實際執行時間是否比預估更長。
4. 系統狀態是否剛好處在擴縮或資源回收過程中。

如果模型只看平均值，可能會選到「平均看起來不錯，但壞情況很差」的安排方式。Distributional SAC 的想法是讓模型同時看到好情況與壞情況，再依照風險偏好做決策。對本專題而言，這很適合用在共享 GPU 平台，因為我們不只追求平均完成時間，也希望避免某些工作因錯誤配置而等待過久或執行失敗。

在本系統中，模型面對的是一組有限的候選安排，例如「哪個等待中的工作」應該搭配「哪個可用節點與 GPU 資源」。Distributional SAC 會為每個候選安排估計可能結果的分布，再用較保守的下尾風險指標輔助選擇。白話來說，就是不要只問「平均表現最好的是誰」，也要問「如果情況不順，哪個選擇比較不容易造成嚴重後果」。

目前實作方向包含：

1. 使用分布式 critic 估計不同排程選擇的結果分布。
2. 保留 Soft Actor-Critic 的探索能力，避免模型過早固定在單一策略。
3. 加入風險敏感決策，讓模型可以偏向較穩定的資源配置。
4. 使用真實系統紀錄回饋訓練，降低模擬環境與真實環境的落差。

整體訓練與評估流程如下：

1. 先在模擬環境中建立不同的工作到達情境。
2. 讓模型在模擬環境中學習資源分配策略。
3. 將訓練好的模型放到真實系統中測試。
4. 收集真實系統中的執行紀錄，回頭改善模型。
5. 比較基本排程規則、平均值導向模型，以及風險敏感模型在不同情境下的表現。

這樣的流程可以讓我們先在安全的模擬環境中訓練，再逐步把成果帶到實際系統，降低直接上線的風險。

## 4.1 目前完成項目

### (1) 平台建置與操作流程

目前系統已完成主要平台建置，並整理出較清楚的部署與驗證流程。使用者可以透過登入節點提交工作，系統則自動在背後完成節點啟動、工作排程、GPU 分配與結果輸出。

此外，也已完成使用教學與系統文件整理，方便後續展示與交接。

### (2) 智慧排程已可在真實系統中運作

目前強化學習模型已經不是只存在於模擬環境，而是能夠實際參與真實系統中的工作排序。也就是說，當使用者提交工作後，模型會根據當下的系統狀態給出建議，並影響工作的優先順序。

這代表本專題已經從「理論設計」進入「真實系統驗證」階段。

### (3) 模型已可初步參與資源放置

除了決定哪個工作先執行之外，目前系統也能在受控情況下，讓模型參與工作應該放到哪個節點執行的決策。這對本專題非常重要，因為它表示我們不只是做工作排序，而是逐步朝向完整的資源分配系統發展。

### (4) 監控與展示介面已建立

目前系統已可清楚呈現下列資訊：

1. 等待中的工作數量。
2. 各計算節點是否已啟動、正在執行或閒置。
3. GPU 的實際使用率。
4. GPU 切分資源的使用情形。
5. 智慧模型最近是否有做出決策，以及決策結果為何。
6. 一個工作從提交到開始執行的完整過程。

這些功能除了有助於除錯，也非常適合作為專題展示內容。

## 4.2 已發現問題與修正

### (1) 節點回收後狀態不一致

在先前測試中，我們發現當 GPU 節點因暫時沒有工作而被回收後，系統有時無法正確辨識它已經離線，導致後續工作啟動時出現狀態不同步的問題。

目前已完成修正，讓系統在節點回收與重新啟動時，能先更新狀態，再重新接受新工作。這項修正的目的，是提高真實環境長時間運行時的穩定性。

### (2) GPU 資源描述與實際環境不一致

我們也曾遇到 GPU 資源描述方式與容器內實際可見硬體不完全一致的問題，導致部分工作卡住無法正常結束。經過調整後，目前這項問題已排除，後續測試工作皆能正常完成。

### (3) 智慧模型效果尚未超越基本規則

雖然模型已可在真實系統中運作，但目前在模擬環境下的效能比較結果顯示，早期以平均值為主的模型尚未穩定超越基本排程規則。這是目前最需要誠實面對的結果。

因此後續模型方向會改成 Distributional SAC：讓模型學習每個決策可能造成的結果分布，並加入風險敏感判斷。這樣可以更符合真實共享 GPU 平台的需求，因為排程系統不只要追求平均速度，也要避免少數工作因錯誤配置而出現很差的等待時間或失敗風險。

3. 若要讓模型真正優於既有方法，還需要更好的訓練資料、更貼近真實情況的模擬環境，以及更大的測試規模。

## 4.4 後續改進方向

根據目前進度，後續工作建議集中在以下幾個方向：

1. **改用風險敏感的 Distributional SAC**：讓模型學習每個資源配置的結果分布，並避免選擇壞情況風險過高的安排。
2. **讓模擬環境更接近真實系統**：目前模型多半在模擬環境中學習，但若模擬過於理想化，就可能導致模型在真實系統中的效果不如預期。
3. **擴充到多台主機情境**：若要真正展示智慧資源分配的價值，需要讓模型在更大的叢集上做決策，而不是只在單機環境中測試。
4. **持續收集真實執行紀錄**：讓模型能從真實工作資料中持續修正，而不是只依賴人工設計的模擬情境。
5. **進行更公平的效能比較**：在相同條件下比較基本規則、平均值模型與風險敏感模型，才能更清楚知道模型是否真的帶來效益。
6. **強化展示與報告內容**：將目前的系統流程、監控畫面、測試結果整理成更完整的圖表與簡報，提升專題成果的呈現品質。
